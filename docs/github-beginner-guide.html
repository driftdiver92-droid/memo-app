1. Git と GitHub とは？

Git（ギット）

ファイルの「変更履歴」を記録するしくみ。

たとえば、レポートを書いていて「さっきの方がよかった…」と思ったことはありませんか？
Git を使うと、好きなタイミングで「セーブポイント」を作れます。
いつでも過去の状態に戻せるので、安心してコードを変更できます。

普通のファイル管理

レポート_v1.docx
レポート_v2.docx
レポート_最終版.docx
レポート_本当の最終版.docx
→ ごちゃごちゃ…

Git を使った管理

レポート.docx
├ セーブ1: 「下書き完成」
├ セーブ2: 「図を追加」
├ セーブ3: 「FB反映」
└ セーブ4: 「最終確認OK」
→ スッキリ！

GitHub（ギットハブ）

Git で管理したファイルを、インターネット上に保存・共有できるサービス。

Git だけだと、履歴はあなたのPCの中だけにあります。GitHub にアップすると：

  • PCが壊れてもコードが残る（バックアップ）
  • 他の人にコードを見せられる（共有）
  • チームで一緒に開発できる（共同作業）
┌─────────────┐ ┌─────────────────┐ │ あなたのPC │ ── push ──→ │ GitHub（雲の上） │ │ （ローカル） │ ←── pull ── │ （リモート） │ └─────────────┘ └─────────────────┘ Git で管理 インターネット上に保存

2. 全体の流れ（地図）

今回やったことの全体像です。番号順に進めました。

【事前準備】（1回だけやればOK） ① Git の初期設定（名前・メールアドレス） ② GitHub CLI のインストール ③ GitHub へのログイン 【プロジェクト開始】（プロジェクトごとに1回） ④ git init — フォルダを Git リポジトリにする ⑤ gh repo create — GitHub にリポジトリを作る 【日常の作業】（何度も繰り返す） ⑥ ファイルを作成・編集する ⑦ git add — 記録したいファイルを選ぶ ⑧ git commit — セーブポイントを作る ⑨ git push — GitHub にアップする

3. 事前準備でやったこと

①Git の初期設定

git config --global user.name "driftdiver92-droid"
git config --global user.email "driftdiver92@gmail.com"
なぜ必要？
Git は「誰が」変更したかを記録します。 名前とメールアドレスを設定しておくと、 すべてのセーブポイント（コミット）に「この人が変更した」と記録されます。
--global とは？
このPCのすべてのプロジェクトに適用される設定という意味です。 1回設定すれば、もうやり直す必要はありません。

②GitHub CLI（gh）のインストール

sudo apt install gh -y
単語意味
sudo管理者権限で実行する（PCのパスワードが必要）
aptUbuntu/Linux のソフトインストールツール
installインストールする
ghGitHub CLI（ターミナルから GitHub を操作するツール）
-y「本当にインストールする？」の確認を自動で「はい」にする

③GitHub へのログイン

gh auth login

ブラウザが開き、GitHub アカウントでログインしました。これで、ターミナルから GitHub にアクセスできるようになりました。

4. 実際の操作と解説

④git init — リポジトリの作成

git init

フォルダの中に .git という隠しフォルダを作りました。ここに変更履歴がすべて保存されます。

Git Hub-TEST/ ├── .git/ ← git init で作られた（履歴の保存場所） ├── index.html ├── style.css └── app.js
たとえると…
ノートの1ページ目を開いて「ここに記録していく」と決めた、ということです。 
git branch -m main

ブランチの名前を master から main に変更しました。最近は main が世界標準の名前です。

ブランチって？
「作業の流れ」のこと。今は main という1本だけ。 将来チーム開発するときに「枝分かれ」させて使いますが、 今は「main = メインの作業場所」とだけ覚えればOKです。

⑤ファイルの作成

3つのファイルを作りました（メモアプリ本体）：

ファイル役割たとえると
index.html画面の骨組み家の設計図
style.css見た目のデザイン壁紙や家具の配置
app.js動作のロジック電気やスイッチの配線

⑥git add — 記録対象を選ぶ

git add index.html style.css app.js

「この3つのファイルを、次のセーブポイントに含めるよ」と Git に伝えました。

なぜ add が必要？
Git では、変更したファイルを「自動で全部セーブ」しません。 「どのファイルをセーブするか」を自分で選びます。
作業フォルダ ステージング セーブポイント （変更した場所） ── add ──→（セーブ待ち）── commit ──→（記録完了！） index.html ── add ──→ [index.html] style.css ── add ──→ [style.css ] ── commit ──→ セーブポイント完成！ app.js ── add ──→ [app.js ]
たとえると…
引っ越しのとき、段ボールに入れる荷物を選んでいる段階です。
git add = 段ボールに入れる
git commit = 段ボールにフタをして「荷物リスト」を書く

⑦git commit — セーブポイントを作る

git commit -m "feat: メモアプリの実装（HTML/CSS/JS）"
部分意味
git commitセーブポイントを作るコマンド
-m "..."セーブポイントに付ける説明メッセージ
feat:「新機能の追加」という種類を表すラベル

コミットメッセージのラベル（よく使うもの）：

ラベル意味使う場面
feat:新しい機能機能を追加したとき
fix:バグ修正不具合を直したとき
docs:ドキュメント説明文やREADMEを変えたとき
refactor:リファクタリング動作は変えずコードを整理したとき
test:テストテストを追加・修正したとき

今回の履歴：

git log --oneline の結果：

5403d8a feat: メモアプリの実装（HTML/CSS/JS）    ← 2回目のセーブ
ad2e715 初回コミット: READMEを追加                ← 1回目のセーブ

左の 5403d8a はセーブポイントのID（自動生成）。過去に戻りたいときに、このIDを使います。

⑧gh repo create — GitHub にリポジトリを作成

gh repo create memo-app --public --source=. --push \
  --description "初心者向けメモWebアプリ（HTML/CSS/JS）"

GitHub にリポジトリを作り、コードをアップしました（1コマンドで全部やった）。

オプション意味
memo-appリポジトリの名前
--public誰でも見られる公開リポジトリにする
--source=.今いるフォルダ（.）をアップロード元にする
--push作成と同時にコードをアップする
--description "..."リポジトリの説明文
補足：--private にすると非公開（自分だけ見られる）リポジトリになります。

⑨git push — GitHub にアップする

git push

PCにあるセーブポイント（コミット）を、GitHub にアップロードしました。

あなたのPC GitHub ┌──────────────┐ ┌──────────────┐ │ セーブ1: README │ ── push ──→ │ セーブ1: README │ │ セーブ2: アプリ │ │ セーブ2: アプリ │ └──────────────┘ └──────────────┘
push と commit の違い：

コマンドやることどこに保存？
git commitセーブポイントを作るあなたのPCの中だけ
git pushセーブポイントをアップGitHub（インターネット上）
commit だけでは GitHub には反映されません。push して初めて GitHub に反映されます。

5. 今後よく使うコマンド一覧

毎日使うコマンド（3つだけ覚えればOK）

# 1. 変更したファイルを選ぶ
git add ファイル名

# 2. セーブポイントを作る
git commit -m "変更内容の説明"

# 3. GitHub にアップする
git push

状況を確認するコマンド

# 今の状態を見る（何が変更されたか）
git status

# セーブポイントの履歴を見る
git log --oneline

# 前回のセーブから何が変わったか見る
git diff

git status の読み方

$ git status

ブランチ main

Changes not staged for commit:     ← 変更したけど add してないファイル
    modified:   app.js

Untracked files:                   ← 新しく作ったけど Git が知らないファイル
    newfile.txt

nothing to commit                  ← 全部セーブ済み。何もすることなし！

6. よくある質問

Q: add と commit を毎回やるのは面倒。まとめてできない？

A: できます。でも分けたほうが安全です。

# 全ファイルを一括で add + commit する方法
git add -A && git commit -m "メッセージ"
注意：-A は全ファイルを対象にするので、 間違えてパスワードファイルなどをアップしてしまう危険があります。 慣れるまではファイル名を指定する方法がおすすめです。

Q: 間違えて commit したら取り消せる？

A: 直前の commit なら取り消せます。

# 直前の commit を取り消す（ファイルの変更は残る）
git reset --soft HEAD~1

Q: push した後に間違いに気づいたら？

A: 新しい commit で修正するのが安全です。

# 間違いを修正して…
git add 修正したファイル
git commit -m "fix: ○○を修正"
git push

Q: commit メッセージは日本語でいい？

A: 個人プロジェクトなら日本語でOKです。チーム開発やオープンソースでは英語が一般的です。
